# Architecture Review — Phase 0

**Role and scope:** Architect-only independent review of the accepted execution plan and its binding product/decision contracts. This is a design review, not implementation evidence and not a QA, security/privacy, legal-clearance, human-approval, or publication disposition. The working identity remains private and **NOT PUBLISHED**.

**Prior-gate context:** `evidence/reviews/planner-consensus-review.md` records a Planner `APPROVE`. That is evidence that planning dependencies and ownership were reviewed; it is not proof that the architecture is internally implementable. This review independently examines the stated architecture.

**Authorities reviewed:** `docs/PRODUCT_SPEC.md` §§Required domain capabilities, Runtime and architecture constraints, Safety and authority prohibitions, Delivery phases and gates; `docs/IMPLEMENTATION_PLAN.md` §§1–4; ADR 0001 §§Store-location resolution, SQLite opening and transaction invariants, Journal mode and filesystem safety, Schema/migrations/recovery; ADR 0002 §§One canonical command/application layer, Optional watch adapter, Optional MCP adapter, Adapter lifecycle/failure isolation; ADR 0003 §§Canonical data and invariants, Snapshot query boundary, Export and adapter boundaries; `docs/ACCEPTANCE_MATRIX.md` §§Common execution contract, A–G; `docs/THREAT_MODEL.md` §§Assets and trust zones, Security invariants, Threats; `docs/PRIVACY.md` §§Data categories, Data minimization/default views, Exports/receipts/events/errors/evidence, Local process/transport boundaries; `docs/research/UPSTREAM_REUSE_DECISION.md` §§Decision, Reusable concepts/not source code, Decision constraints; and `docs/brand/NAME_CLEARANCE.md` §§Publication gate, Neutral internal namespace and rename decision criteria, Rename-impact matrix.

## Architecture blockers

| # | Finding and exact anchors | Why this blocks implementation | Minimal corrective action |
|---|---|---|---|
| A1 | **The canonical snapshot/ViewModel ownership contradicts the declared dependency graph.** Plan §2.1 assigns `internal/view` “versioned ViewModel construction, redaction, renderers,” while its allowed direction is `transport → app → domain/ports` and says `view` merely consumes query snapshots. Plan §2.2 makes `QueryHandler.Query` return `ViewModel`; Plan §4/P5-A assigns both `internal/view` and `internal/app/query`; ADR 0003 §Snapshot query boundary requires `QueryHandler.Query` to perform authorization, selection, redaction, ordering, and return the versioned immutable `ViewModel`. These statements leave either (a) `internal/app` importing `internal/view` to construct its declared return type, contrary to the dependency rule, or (b) `internal/view` rebuilding query/redaction semantics after the application query, contrary to ADR 0003. | The P5-A split cannot be implemented without inventing a new dependency edge or duplicating semantic ownership. That risks divergent CLI/MCP/renderer redaction and violates the required single-snapshot boundary. | Before P5 fan-out, freeze one direction: make an application-owned, transport-neutral `internal/app/query` package own the versioned DTOs, snapshot assembly, authorization, redaction-policy invocation, and deterministic ordering; make `internal/view` renderer-only (`ViewModel → TTY/JSON/Markdown/HTML`). ## Findings with no present architecture blocker

### Package and adapter boundaries

- The intended core direction is sound once A1 is corrected: CLI/MCP/watch decode transport input and call shared application command/query handlers; SQLite, Git, platform, and integration implementations sit behind ports (Plan §2.1; ADR 0002 §One canonical command/application layer). `cmd` is composition-only, and neither CLI nor MCP owns SQL or a competing state machine.
- Daemonless behavior is appropriately a correctness boundary, not an operational preference. ADR 0002 §§CLI contract and Optional watch adapter require a stopped watch to have no correctness effect; watch re-reads canonical state, uses derived idempotency keys, and only notifies after a committed transition. MCP has explicit lifecycle, strict validation, cancellation propagation, explicit scope selection, and no default listener (ADR 0002 §§Optional MCP adapter and Adapter lifecycle/failure isolation). These are testable through matrix `OMG-AC-002`, `OMG-AC-015`, `OMG-NFR-006`–`007`, and `SEC-T18`–`020`.
- Proof harness isolation is architecturally correct as specified: physical `proofs/pygmalion` and `proofs/zoomzi` boundaries, released CLI/OMGCP-only consumption, and prohibition of core imports, build tags, fixtures, or name-specific branches (Plan §2.1 and §§Phase 7–8; matrix `OMG-PRO-008`, `OMG-PYG-007`, `OMG-ZOO-002`, `OMG-ZOO-006`). Generic opaque import records are compatible with the core only if their schema/authority semantics remain the P2-A generic import contract; the proof harnesses must not become core dependencies.

### Data ownership, concurrency, and recovery

- SQLite is correctly canonical and repository transactions are correctly scoped: application services define the outcome, while a write transaction contains the domain mutation, audit event, and idempotency receipt (ADR 0001 §SQLite opening and transaction invariants; ADR 0003 §Canonical data and invariants). The stated `Store.Write(ctx, idempotencyKey, fn)` boundary and immutable receipts support repeat-safe mutation.
- The plan/ADRs provide adequate architectural semantics for atomic claim, token consumption, and exactly-once domain notification: short writes, foreign keys per connection, bounded busy handling, deterministic retry only for transient busy/locked errors, cancellation, and no retry without an idempotency key (ADR 0001 §SQLite opening and transaction invariants; Threat Model §Security invariants 6 and TM-04/TM-12). `OMG-AC-005`/`006` and `OMG-CAP-005`/`008` specify the observable race and no-duplicate notification tests. Implementation must encode the active-claim and unblock-delivery uniqueness invariants in the transaction/constraints rather than infer them from renderers or watch delivery.
- WAL is conditional rather than assumed: filesystem eligibility, returned-mode verification, sidecar creation/locking, and a recorded DELETE-journal fallback are all explicit (ADR 0001 §Journal mode and filesystem safety). This supports local-file safety and preserves a non-WAL recovery path.
- Migration authority and recovery are mostly safe: non-mutating open/status/plan, a plan ID, per-apply approval binding, verified post-plan/pre-apply backup, checksum/version fail-closed behavior, and non-destructive restore planning are specified (ADR 0001 §Schema, migrations, and recovery; Plan §2.3 and §Phase 2; matrix `OMG-AC-016`, `SEC-T14`–`015`). A2 must be repaired before this ownership model is implementable in P4.

### Filesystem, Git, portability, and views

- Store resolution has a viable cross-platform ownership model: Git worktree mode uses `git rev-parse --path-format=absolute --git-common-dir`; bare repositories are rejected for project initialization; non-Git roots use `os.UserConfigDir`; workspace joins are explicit; and private state/sidecars remain untracked (ADR 0001 §Store-location resolution). It covers common-directory sharing, non-Git mode, explicit workspace mode, and safe diagnostic redaction. The required edge fixtures cover spaces/CJK, non-`main`, detached, bare, linked-worktree, and non-Git behavior (Product Spec §Safety and authority prohibitions; matrix `OMG-NFR-003`, `005`, `011`).
- Cross-platform build assumptions are constrained rather than hidden: current stable Go, `CGO_ENABLED=0`, a pure-Go driver behind `Store`, five named targets, platform-sensitive file permission behavior, and CI-only claims for the full matrix are all stated (ADR 0001 §§Language/packaging/driver and Testable acceptance checks; Plan §1 rule 6; matrix `OMG-AC-017`, `OMG-NFR-001`, `OMG-PRO-006`). Clock injection is explicitly available through the `Clock` port and is necessary for TTL and deterministic snapshot fixtures (Plan §2.2; ADR 0003 §§Snapshot query boundary and Selectors/ordering/absence).
- ADR 0003 supplies the right canonical-state rule: one consistent read snapshot, query-layer authorization/redaction/order, immutable versioned DTOs, and renderers that never open SQLite/Git, mutate, authorize, or fetch network resources. Metadata, stable absence values, deterministic ordering, and renderer rollback are specified. A1 is the sole ownership conflict preventing this otherwise viable isolation from being frozen.

### Token, privacy, and authority boundaries

- The principal boundaries are architectural and centralized: `ActorContext` is based on resolved identity/provenance and explicit capabilities, not free-form content; delegation is project/purpose/TTL/one-time/revocation bounded; raw tokens are verifier-only at rest; messages/imports/adapter input are data, never approval; and restricted actions have no command path (Plan §2.2 and §Phase 3; ADR 0002 §One canonical command/application layer; Threat Model §§Security invariants and TM-01/TM-04/TM-10).
- Privacy-safe output has a defined placement: explicit safe field sets and write-time allowlists for events/receipts/errors/evidence, default redaction before all renderers, untracked private local metadata, no default network/telemetry, and self-contained restrictive-CSP HTML (Privacy §§Data minimization/default views, No telemetry/network behavior, Exports/receipts/events/errors/evidence; ADR 0003 §§Snapshot query boundary and Format contracts). This review makes no finding that the controls are implemented or effective.

### Sequencing, recovery, reuse, and identity constraints

- The dependency DAG correctly keeps P3/P4 behind P2-A/B contracts, P5 behind P3/P4 facts, the RC behind the named retain/rename decision, and both proof harnesses behind the D6 RC gate; Zoomzi also waits for completed Pygmalion evidence and its own approval (Plan §3 and §§Phase 6–8; Product Spec §Delivery phases and gates; matrix `OMG-RG-001`–`003`). C1/C2/C3/C4 recovery boundaries preserve fixtures/proofs and forbid destructive Git cleanup (matrix §Common execution contract). This is an executable sequencing contract, not proof that any gate is satisfied.
- Greenfield-only reuse is compatible with the package plan: concepts may inform original design, but no upstream source/layout/API/test/prompt logic is authorized for copying; future dependencies require exact version/checksum/license review (Reuse Decision §§Decision, Reusable concepts/not source code, Decision constraints). It prevents upstream adapter or relay assumptions from contaminating the local core.
- The private name constraint is properly contained in neutral internal module/artifact naming and a pre-RC human retain/rename decision. Any later rename invalidates RC/proof/parity artifacts and requires explicit state/protocol/config migration planning; it does not authorize public namespace, registry, domain, or release activity (Name Clearance §§Publication gate, Neutral internal namespace and rename decision criteria, Rename-impact matrix; Plan §Phase 2 and §Phase 6). No name-clearance or publication conclusion is made here.

## Non-blocking implementation risks

1. **SQLite uniqueness needs concrete schema tests.** The contracts demand one active exclusive claim and exactly-once unblock outcome, but implementation must choose and test the corresponding unique indexes/conditional state representation and receipt replay behavior. Matrix `OMG-AC-005`/`006`, `OMG-CAP-005`/`008`, and `SEC-T16` provide the required observable cases.
2. **Filesystem classification and no-follow behavior are platform-sensitive.** The unknown-filesystem-to-DELETE default is conservative, but the platform adapter needs tested Windows reparse/junction and POSIX special-file handling rather than path-string checks (ADR 0001 §Journal mode and filesystem safety; Threat Model TM-06/TM-07; matrix `SEC-T09`–`011`).
3. **Adapter event delivery is deliberately at-least-once/best-effort.** It must stay notification-only and idempotent; it cannot be used to establish mailbox, unblock, or claim correctness (ADR 0002 §§Optional watch adapter and Adapter lifecycle/failure isolation).
4. **Redaction is not a proof of comprehensive sanitization.** The design correctly treats heuristic redaction as fallback; field minimization/allowlists must be the primary control and evidence must remain secret-free (Privacy §§Data minimization/default views and Redaction limitation; Threat Model TM-03).
