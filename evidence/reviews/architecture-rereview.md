## Full architecture re-evaluation

### Package boundaries, ports, and canonical views

- The package graph is coherent: Plan §2.1 assigns transports to typed decoding, `internal/app` to handlers/use cases/receipts/snapshots, ports to infrastructure abstractions, and adapters to their defined concerns. Its allowed direction (`transport → app → domain/ports`, implementations `→ ports`) keeps `cmd` as composition and excludes adapter-owned domain SQL/state machines. ADR 0002 §One canonical command/application layer independently requires CLI, MCP, and watch to submit typed requests to shared handlers rather than duplicate SQL, authorization, validation, or state transitions.
- The corrected query graph is internally closed. Plan §§2.1–2.2 and §5/P5-A define app-owned immutable DTO construction before renderer entry; ADR 0003 §§Snapshot query boundary and Format contracts define a transport-neutral, versioned snapshot consumed by all four renderers. The selected facts, scope authorization, default redaction, ordering, metadata, absence states, and cursor are determined before rendering. This preserves one consistent snapshot and leaves renderer failure outside command-outcome establishment.
- Canonical view coverage remains aligned with the product contract: ADR 0003 §§Selectors, ordering, and absence and Plan §§2.4, 5/P5-A cover `me`, `tree`, `task`, `all`, and `git`, deterministic ordering and explicit `unknown|not_applicable|missing`; Product Spec §§Required domain capabilities and Required product surfaces require the same durable facts and output forms. The matrix rows `OMG-AC-007`, `OMG-AC-012`–`015`, and `OMG-CAP-014` identify future observables without being treated here as completed evidence.

### SQLite concurrency, migrations, and recovery

- ADR 0001 §§SQLite opening and transaction invariants and Schema, migrations, and recovery provide a single store boundary: transaction-scoped repositories, atomic outcome/audit/receipt writes, per-connection foreign-key verification, bounded busy handling, short transactions, deterministic idempotency-key-based retry limited to transient busy/locked results, and cancellation. Plan §2.2 freezes a matching `Store` interface; Plan §2.3 assigns the migration runner and checksum rules solely to P2-B.
- The migration topology is now implementable without a cross-lane immutable-file conflict. `0001_foundation.sql`, `0002_coordination.sql`, `0003_reservations.sql`, and `0004_git_assets.sql` have ordered, exclusive owners in Plan §2.3 and §3. P2-B owns execution—not schema edits for the Phase-4 lanes—and Plan §4/D4 fixes P2-B’s authorized application sequence at `0003` then `0004`. ADR 0001 requires plan-before-apply, exact approval binding, verified backup after planning and before application, checksum/version fail-closed behavior, and rollback retention. Acceptance Matrix `OMG-AC-016`, `OMG-NFR-002`, `SEC-T14`–`017`, and Gate interpretation retain the per-apply approval and preservation obligations as future verification contracts.
- WAL is properly conditional rather than assumed. ADR 0001 §Journal mode and filesystem safety requires eligibility classification, returned-mode verification, WAL sidecar/locking verification, DELETE fallback, and fallback audit recording. This is compatible with the local-first canonical store and does not convert WAL into a prerequisite.

### Lifecycle, adapters, filesystem, and Git portability

- ADR 0002 §§CLI contract, Optional watch adapter, Optional MCP adapter, and Adapter lifecycle/failure isolation preserve a daemonless core: watch is notification-only/best-effort, re-reads canonical state, uses derived idempotency keys, and a stopped watch does not affect correctness. MCP uses shared handlers, strict framing, explicit scope selection, cancellation propagation, and no default listener. Plan §5/P5-B matches these adapter boundaries.
- ADR 0001 §Store-location resolution provides distinct Git-worktree, non-Git, and explicit-workspace paths. Git worktree mode resolves the absolute Git common directory; bare repositories are rejected for project initialization; non-Git state is under the platform user configuration root; private state and sidecars are untracked. Product Spec §Runtime and architecture constraints and Acceptance Matrix `OMG-AC-003`, `OMG-NFR-003`–`005`, and `OMG-NFR-011` maintain the relevant portability contracts.
- Plan §4/D4 confines Git inventory to argv-only, read-only discovery and cleanup-plan output. ADR 0003 §Canonical data and invariants makes Git observations immutable and `SAFE_TO_REMOVE` non-authorizing. Product Spec §Safety and authority prohibitions and Matrix `OMG-AC-010`, `OMG-PRO-003`, `OMG-NG-005`, and `OMG-CAP-012`–`013` preserve the observational/adoption-only boundary.

### Authority, privacy-oriented projection, proof isolation, and release sequencing

- The authority graph remains centralized: Plan §2.2 defines `ActorContext` from resolved identity/provenance/capabilities rather than content; ADR 0002 §§One canonical command/application layer and Optional MCP adapter treat messages, requests, and approval-shaped text as untrusted input. Product Spec §Safety and authority prohibitions preserves absence of delegated high-impact authority. These are architecture constraints, not a finding about their implementation or effectiveness.
- Projection placement is consistent with the stated sensitive-data boundary: Plan §2.1 makes app/query apply default redaction before renderer use, while ADR 0003 §§Canonical data and invariants, Snapshot query boundary, and Format contracts requires safe data handling before rendering and transport-neutral view DTOs. The Acceptance Matrix rows `OMG-AC-012`–`013`, `OMG-PRO-004`, `SEC-T04`–`005`, and `PRIV-T01`–`05` remain future proof obligations.
- Proof isolation is explicit. Plan §2.1 and §§2.4, 7, and 8 place Pygmalion and Zoomzi outside the core boundary, permit only public CLI/OMGCP consumption and generic opaque records, and prohibit proof-specific core imports, fixtures, build tags, or conditional branches. ADR 0003 §Export and adapter boundaries reaches the same conclusion; Matrix `OMG-PRO-008`, `OMG-PYG-007`, `OMG-ZOO-002`, and `OMG-ZOO-006` are aligned.
- RC and proof sequencing remains acyclic and gated: Plan §3 requires P2-A before P3/P4, P3/P4 facts before P5, a named retain/rename decision before the local RC pin, D6 before either proof, Pygmalion completion before Zoomzi, and a replacement RC plus proof/parity reruns after identity change. Product Spec §Delivery phases and gates and Matrix `OMG-RG-001`–`003` and Gate interpretation preserve these dependencies. The working publication status remains `NOT PUBLISHED` as stated by the product authority; this review does not assert any publication-related action or gate outcome.

## Non-blocking architecture risks

1. **Schema-level expression of concurrency invariants:** ADR 0003 §Canonical data and invariants requires one active exclusive claim and exactly-once unblock outcome, while ADR 0001 §SQLite opening and transaction invariants supplies the transaction rules. The implementation still needs concrete constraints/indexes and fixtures to make those invariants observable; the relevant future contracts are `OMG-AC-005`–`006`, `OMG-CAP-005`/`008`, and `SEC-T16`–`017`.
2. **Filesystem classification remains platform-sensitive:** ADR 0001 §Journal mode and filesystem safety requires conservative unknown-to-DELETE behavior, but supported OS adapters must accurately distinguish local eligibility and unsafe special-file forms. Matrix `OMG-NFR-011`, `SEC-T09`–`011`, and `SEC-T17` retain that proof burden.
3. **Adapter delivery is deliberately non-canonical:** ADR 0002 §§Optional watch adapter and Adapter lifecycle/failure isolation permits best-effort, at-least-once notification. This stays sound only if notification consumption remains idempotent and no domain correctness is inferred from delivery.
4. **Redaction scope must remain DTO-field-led:** ADR 0003 §Snapshot query boundary and Format contracts place default projection filtering before renderers. The architecture does not make heuristic matching a substitute for explicit safe fields and allowlists; the listed matrix rows preserve this as an implementation verification obligation.

## Architecture disposition

Both prior blockers are resolved by current, mutually consistent plan and ADR anchors. No architecture blocker remains in the re-reviewed categories. This disposition is limited to plan/contract consistency and does not satisfy any implementation, QA, security, legal, publication, or human approval gate.
